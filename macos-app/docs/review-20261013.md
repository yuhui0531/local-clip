## PNG/TIFF preservation follow-up

The user subsequently authorized repairing the image-fidelity risk. The earlier decision to defer this change is superseded by the following implementation. No existing user database was opened or modified during validation.

- Capture and ingest retain every supported original representation. Coexisting PNG and TIFF are not treated as proof of equivalence; no decoder is used to rewrite original bytes.
- Startup image compaction is removed. Public `withoutRedundantTIFF` and `compactRedundantImages()` entry points remain available for API compatibility but preserve their input/history; compaction reports zero changes. No schema, user-setting, quota-default or fingerprint-format migration is required.
- Full-payload canonical hashing still ignores representation order while including each original type and byte stream. Different TIFF pages, metadata or bit depth cannot be merged merely because PNG matches. Identical bytes still share BLOB storage. A newly captured PNG+TIFF payload can intentionally be a separate record from a legacy PNG-only record.
- The existing 50 MiB capture cap and store quota now count all original representations. An image previously admitted only by silently discarding TIFF may now be rejected as a whole. Existing quota eviction rules still apply to ordinary records; protected records retain complete payloads. This is an intentional preservation tradeoff, not a larger storage allowance.
- Exact successful self-writes are filtered before body reads, avoiding needless on-demand TIFF generation. The receipt marker and pasteboard generation are rechecked; a concurrent user copy is still captured. Existing failed-write and in-flight guards remain. PNG-only history still supplies TIFF on demand to clients that request it.

### 2. 已确认并修复的问题

**导出租约占满 50 MiB 导出预算（已修复、已验证）**
- 触发条件：拖出大幅原始 TIFF（例如约 27 MB 的未压缩 TIFF）时，连续或多选导出的合计超过 50 MiB。
- 根因：每次文件承诺都先写入一份自有租约，再复制到目标。租约原本要等每分钟一次的 `cleanExports` 在 10 分钟后才回收。改为导出原始 TIFF 后，租约比旧的第 0 帧 PNG 大得多，于是第二次导出就返回 `quotaExceeded`。数据仍然安全（不写目标文件、不淘汰历史），但拖出失败。
- 修复（`ContentExportProvider.swift`，+2 行）：复制尝试结束后，不论成功还是失败，都立即删除本次租约（`defer`）。目标拿到的是独立副本。配额检查、校验和不覆盖逻辑都没有改变。
- 回归测试：新增 `largeTIFFExportsReleaseLeaseAfterCopy`。修复前失败（第二次导出返回 `quotaExceeded`、目标文件缺失、租约残留，见 `lease-budget-before.log`），修复后通过。成功和失败用例都补充了"导出目录不残留本次租约"的断言。变异验证：临时去掉修复行后，5 个成功用例和 existing-file 用例都会失败，恢复后通过。

**多选拖出时导出依赖主线程、多份租约同时存在（复查中发现，已修复；其中一部分只有推理依据）**
- 触发条件：多选拖出多个大幅原始 TIFF。AppKit 会背靠背地索取各个承诺，不等前一个完成；而每个承诺的链路都要多次回到主线程。
- 已复现的部分：在测试中让主线程每 40 ms 阻塞一次（模拟拖放期间的界面负载），3 张约 27 MB 的 TIFF 同时导出，有 2 张返回 `quotaExceeded`、目标文件缺失，5/5 复现（`concurrent-busy-main-*.log`）。根因是"复制并释放租约"这一步要等主线程，而存储 actor 继续写下一份租约；主线程长时间被占用时，导出会完全停滞。
- 修复（`ContentExportProvider.swift`）：① `writePromiseTo` 不再跳回主线程，只读配置在 nonisolated 上下文中捕获，读取、写租约、校验、复制、释放都在后台执行；② 新增 `ExportLeaseQueue`，按顺序逐个执行"读取 → 租约 → 复制 → 释放"，保证同一进程同时最多一份租约，内存中也只驻留一份载荷。
- 验证：新增 `concurrentLargeTIFFPromisesAllComplete`（3 × 约 27 MB，任意两份同时存在就超出预算，并模拟繁忙主线程）。修复后 5/5 通过（`concurrent-busy-main-after-*.log`）。
- **未被证明的部分**：变异验证显示，去掉串行队列、只保留"脱离主线程"时，这个测试仍然通过（`concurrent-mutation-no-queue.log`）；直接轮询导出目录也没观察到重叠。原因是本地 APFS 上的复制是克隆，几乎瞬间完成。队列防护的是慢速目标卷（U 盘、网络共享）的场景：第一个文件复制期间，它的租约一直存在，第二个导出写租约就会超出预算。这是推理得出的结论，**本轮没有复现**，需要真实拖到慢速卷上验证。代价是全局串行：一个慢速复制会让后续导出排队。
- 回调线程：完成回调现在从后台线程调用。AppKit 允许在任意线程调用文件承诺的完成回调，旧代码的读取和复制原本就在后台执行。

**发布门禁没有运行文件承诺测试（测试遗漏，已修复）**
- 根因：`imageFilePromisePreservesOriginalBytes` 和 `imageFilePromiseFailureLeavesDestinationAndHistorySafe` 受 `LOCALCLIP_NAMED_TEST` 门控，而 CI（`test.sh --no-parallel`）没有设置这个变量。
- 修复：这两组测试不访问任何剪贴板，因此去掉门控。快照上的 CI 同款串行运行已确认它们实际执行并通过。

### 5. 权限归属：准确的阻塞原因

- 本轮执行环境是 Claude 桌面应用。从这里启动的 event-driver 返回 `canPost=false`、`trusted=false`（`native/permission-state.json`）。
- 用 `responsibility_get_pid_responsible_for_pid` 做只读探测，确认 TCC 责任进程是 `~/Library/Application Support/Claude/claude-code/2.1.295/…/claude.app`，签名标识为 `com.anthropic.claude-code`（Developer ID，Anthropic PBC，Q6L2SF6YDW），DR 基于标识符和团队（`native/responsibility-probe.*`）。上一轮授予 ChatGPT 和 event-driver 的权限对本环境都不生效。
- 隔离 GUI 包是 ad-hoc 签名，DR 为 `cdhash`，**每次重建都会让原有的辅助功能授权失效**。上一轮"隔离应用 AX 检查为 false"的记录（09:19）早于用户的授权，而本轮新包的 cdhash 已经变化。因此，系统设置里旧条目的开关状态不能作为对新包生效的依据。
- 按标准授权流程，向用户提供了准确的授权对象，**用户选择不授权**。代理没有修改 TCC 数据库，没有伪装身份，没有触发权限弹窗，也没有发送任何原生输入事件（驱动日志中只有"未授权，拒绝"的记录）。查询时还观察到用户正在使用电脑；即使已有权限，空闲保护也会拒绝投递。

### 6. 混合格式兼容性（问题 D）结论

- LocalClip 侧：`nativeRoundTripPreservesMultipageTIFF(invalidPNG:)` 证明，无效 PNG + 两页 TIFF 经真实 `NSPasteboard` 往返后，类型和字节都保持不变。在该 fixture 中，PNG 在前、TIFF 在后，本身就符合字母序，所以 LocalClip 没有改变这个用例的顺序。
- 框架侧复现（只使用私有命名剪贴板，见 `mixed-format-appkit-probe.swift` 和 `.log`）：对 AppKit `NSTextView`，"有效 PNG + TIFF"和"仅 TIFF"都能插入附件；"无效 PNG + 有效 TIFF"**无论 TIFF 排在前还是后**，`readSelection` 都失败，插入 0 个附件。`NSImage(pasteboard:)` 在同样输入下则能回退成功。这个探针运行在进程内，并不是 TextEdit 本身，但结果与上一轮在真实 TextEdit 中观察到的空白一致。
- 判断：这是目标应用或 AppKit 文本粘贴路径的格式选择限制。表示顺序不是原因，因此恢复 `declaredTypes` 的顺序也无法解决 D。原始来源应用直接粘贴时同样会失败。
- 可选缓解方案（会改变产品行为，**未实现**，需要产品决策）：① 写出时用 ImageIO 校验，若某个 PNG 无法解码而同一条目中有可解码的 TIFF/JPEG，只在本次输出中省略该 PNG（存储不变），并给出提示；② 提供显式的"按 TIFF 粘贴/导出"选项。代价：每次粘贴都要解码，有额外开销；ImageIO 无法解码、但某些目标应用能解码的变体会被误判；这偏离"忠实重放"的承诺。
