# LocalClip 本轮改动独立验收报告

日期：2026-11-14 · 基线 `5592665` · 验收对象为未提交的工作区改动（22 个已跟踪文件 + 3 个新测试文件 + `performance-history.md`）。本次只验收，未修改实现、测试或文档，未提交。

## 结论：有条件通过

六项准则的功能行为在静默可验证的范围内全部满足，没有发现会损坏数据或贴错目标的问题。存储侧的两项优化经独立基准确认有效；面板提速的数据没有复现。默认全量静默套件连续三次为 541 通过、0 失败、79 跳过。条件有三个：

1. 存储失败弹窗里的“在访达中显示数据目录”按钮会让应用直接退出（问题 1，桌面复测两次复现），需要先修复。
2. 真实粘贴、访达拖出和减弱动态效果下的呈现仍未独立复测：当前进程没有发送鼠标键盘事件的权限，这三项只能引用历史证据。
3. 下面列出的 8 个低到中等问题需要开发者确认或处理，其中第 1 到第 4 项建议在提交前处理。

## 逐项验收

### 1. 配额淘汰与原子性：通过

- 代码（`HistoryStore.swift:189-206`）先循环淘汰最旧普通记录，没有候选后才 `DELETE FROM thumbnails`，仍超再删 `image_text`，最后才抛 `quotaExceeded`。
- 仓库测试 `quotaPressurePreservesSurvivingDerivedRows` 通过。
- 独立探针（临时副本）验证了仓库测试没有覆盖的部分：
  - 分类记录、收藏记录和本次入库记录在越线后保留，各自的缩略图和 OCR 行不变；被淘汰记录的 OCR 文字不再能搜到，幸存记录的仍能搜到。
  - 全部记录受保护后再越线：缩略图被清空，OCR 保留，新记录入库成功。
  - 派生数据清完仍放不下：抛 `quotaExceeded`，`storeRevision`、记录数和 OCR 行数都与操作前一致，`quick_check` 为 ok。
  - 配额预览与应用一致：6 条 25 MiB 记录下调到 100 MiB，预览 `affectedCount=3`，应用 `removed=3`，收藏和最新记录保留，应用后占用不超过新配额。
- 需要知道的一点：新记录比被淘汰的普通记录更大、且没有其他普通候选时，幸存记录的缩略图仍会被整表清空。这符合准则的第二阶段规则，探针第一次运行时正好触发了它。

### 2. 去重与占用统计：通过

- `verifyDuplicateRepresentations`（`:380-400`）只读 `items`、`representations` 和 `blobs.byteCount`，不读 BLOB 正文；按项目序号、类型、长度和摘要比对。
- 仓库测试 `duplicateChecksDescriptorsWithoutReadingStoredBlob` 通过：同长度 BLOB 清零后去重仍成功，读取详情报 `corruptPayload`。探针另验证了摘要列不一致时去重报 `corruptPayload`。
- 占用缓存键为修订号 + 三个目录的实测字节数。探针把每一步结果与无缓存的新实例对照，10 步全部一致：补建缩略图、写入 OCR、清除 OCR、收藏、Exports 新建/扩容/截断、Staging 新建/截断。
- `usage()` 的聚合与 `canCapture` 的预演成本：`performance.md` 和 `delivery.md` 都写明了 1.5 s 的满配额延迟来自“删普通记录再回滚”的预演，缓存没有解决它。表述准确，但这个延迟本身仍然存在（见问题 7）。

### 3. 启动校验与故障恢复：部分不通过（访达定位后应用退出）

- v5→v6 迁移、未知版本拒绝、非 SQLite 文件和外键损坏的 v5 库拒绝打开且字节不变：`SchemaTests`、`HistoryReorderTests` 通过。
- 热日志恢复：`CrashRecoveryTests` 用真实 SIGKILL 覆盖六个断点后打开并恢复，通过。打开阶段的读写连接先回滚热日志再做 `quick_check`，所以首次 `recover()` 跳过检查在这条路径上成立。
- 首次 `recover()` 复用打开校验的前提，探针结果：
  - 打开后、首次恢复前写入的外键损坏，首次恢复不报错，第二次恢复才报 `corruptPayload`。这是复用设计的固有窗口，应用里两步紧挨着执行，可以接受。
  - 首次恢复失败后重试会继续跳过校验（见问题 3）。
- 失败提示：三类文案映射测试通过。桌面复测结果：
  - 不兼容版本的库和随机字节的损坏库分别显示“数据库版本与当前 LocalClip 不兼容…”和“数据库完整性检查未通过…”，三个按钮齐全，弹窗期间库文件的 SHA-256 不变。
  - 移走损坏库后点“重试”：应用新建库并进入历史面板，状态栏项窗口只有一个。
  - 点“在访达中显示数据目录”：访达打开了隔离目录，但应用随即退出，没有回到弹窗（问题 1）。
  - “退出”按钮没有单独点击验证。
- `journal_mode=DELETE`、`synchronous=FULL`、`fullfsync=ON` 和 Schema 版本 6 未被改动，`Schema.swift`、`CommitStrategy.swift`、`Package.swift`、`scripts/` 无差异。

### 4. 面板与粘贴：行为通过，性能收益未证实，真实粘贴未验证

- 等待条件为 `destination != .cards || panel == nil`（`AppDelegate.swift:1028`）：已预创建的面板跳过 32 ms，冷面板、设置和管理窗口保留。80 ms 首屏等待、请求代次校验和草稿保护流程没有改动，`SurfaceTransitionTests` 通过。
- 淡入时长：面板入场 0.12 s，其余 0.20 s，减弱动态效果 0.10 s，按窗口分别计时，测试断言了三个常量。
- `fallbackUsesClipboardFeedback` 通过，走的是“未选择目标应用”的普通回退，传入 `failed=false`，内容确实写入了测试剪贴板。
- `repeatedPasteProducesNoFailureFeedback` 通过：第一次粘贴进行中重入 `perform` 和 `doubleClick`，没有额外提示，第一次发出了粘贴指令。
- 权限回退：`showPasteResult` 仍把它写入状态槽并启动授权轮询；提示条在授权向导可见时不弹。向导不可见时提示条现在也用剪贴板图标，这一分支没有测试。
- 桌面复测（隔离应用，12 条合成记录，4 ms 间隔采样窗口透明度）：
  - 呼出：窗口上屏时透明度为 0，约 0.13–0.14 s 升到 1；首卡选中，搜索框为空，内容完整。
  - 关闭：约 0.12 s 降到 0 后下屏。
  - 关闭后间隔 0.10–0.20 s 立即重开，连续 6 次：每次都完整淡出再淡入，没有透明度来回跳变；最终面板可见、为 key、首卡选中、搜索为空。没有崩溃报告。
  - 局限：探针命令每 100 ms 轮询一次，无法保证重开恰好落在淡出中途；真实快捷键到首帧的时间没有测。
- `FirstFrameDesktopTests` 两个参数通过（首帧为最新首卡，图片已绘制）。但它自建面板并仍然 `sleep(32 ms)`，注释说“与 prepareSurface 一致”已不成立，测不到本轮的跳过逻辑。
- 没有任何测试直接断言“预热面板跳过等待”，这一条只有代码依据；基准数据没有显示出改善（见问题 2）。

### 5. 失效文件预览和导出：通过，访达拖出未独立复测

- 探针覆盖三种情况（两个文件、一个有副本一个没有；另一条完全没有副本）：
  - 详情返回原始引用，`savedFileCopyIndexes` 分别为 `[0]` 和空，读详情和元数据后 `DragFiles` 目录不存在。
  - `loadPayload` 只把有副本的那一项换成 `DragFiles/` 下的路径，字节与原内容一致，SHA-256 与 `file_copies.digest` 相同；没有副本的项保持原路径。
  - 导出句柄：有副本的项可取文件名、字节和恢复后的 URL；没有副本的项文件名为 nil、取字节报 `notFound`、URL 为原路径。
- 显式打开改走 `loadPayload`（`HistoryViewModel.swift:2115`），原格式复制和粘贴本来就走它。
- 提示文案见问题 6。
- 桌面复测：`missingCachedFilePreviewShowsRecoveryHint` 和 `spaceOpensPreviewWindow` 在可见窗口下通过，真实预览窗口显示恢复指引且未生成 `DragFiles`；`DragFileLifecycleTests` 打开命名剪贴板开关后 8 个函数全部通过。
- 访达拖出：需要真实鼠标，当前进程无法发送输入事件，没有复测。历史证据是 `debug-log-2026-11-14-finder-drag.md` 记录的用户真实鼠标拖出，原生会话以 copy 结束，落地文件与 BLOB 的 SHA-256 一致。自动事件在按键状态检查处取消属于工具限制，产品的防误触检查没有被改动。

## 发现的问题

按严重程度排列。没有发现阻断性问题。

**1.（中）存储失败弹窗点“在访达中显示数据目录”后应用直接退出**

- 位置：`AppDelegate.swift:266-279` 的 `promptToRetryStorage`。
- 现象：点击后访达打开了数据目录所在文件夹，弹窗消失，应用进程约在半秒内结束，没有崩溃报告。预期是弹窗保留，用户检查文件后仍可选“重试”或“退出”。
- 复现：隔离验收包（`scripts/build-gui-check.sh`），数据目录放入 `user_version=99` 的库，启动后点第二个按钮。两次复现，第二次有每 0.5 秒的窗口监视记录（01:45:40 弹窗与进程同时消失）。
- 影响：F3 的“定位后继续选择”这条恢复路径不可用；用户要重新打开应用。不影响数据，库文件字节不变。
- 原因未确认。代码在访达激活后对同一个 `NSAlert` 再次 `runModal()`，推测第二次调用立即返回了非按钮的响应值，于是走了退出分支。`delivery.md` 记录这条路径曾验证通过，与本次结果不符。
- 建议：每次循环新建 `NSAlert`，或把“显示数据目录”做成不结束模态的辅助按钮；修复后需要可见窗口复测。

**2.（中）F2 的性能改善没有复现，基准的对比方式不可靠**

- 位置：`macos-app/docs/performance.md` 的 M1 两行和说明，`delivery.md` 开头的“P50 从 94.32 ms 降到 67.98 ms”。
- 证据：当前代码三次 Release 运行的 P50 为 98.9、86.3、90.7 ms。样本呈双峰，一组约 75 ms，一组约 103 ms，P50 落在哪一峰取决于哪组样本略多。
- 原因推断：基准在关闭面板后立刻再次呼出，每次都落在“隐藏首屏仍在准备”的分支上，要等最多 80 ms（`AppDelegate.swift:1026`）。这段等待远大于被去掉的 32 ms，并且它的时序不稳定。文档里“前”是与存储套件同跑测的，“后”是单独跑测的，两者条件也不同。
- 影响：代码上 32 ms 的等待确实去掉了，但“快了 26 ms”这个结论没有数据支持。文档和交付说明的表述需要更正，否则后续会拿它当基线。
- 复现：`LOCALCLIP_PANEL_BASELINE=1 bash scripts/test.sh -c release --no-parallel --filter HistorySubmissionBaselineTests`，在排除五个文件的临时副本中连跑几次，观察 P50 和样本分布。
- 建议：基准在两次呼出之间等隐藏首屏准备完成（或间隔超过 300 ms 的静默期加查询时间），前后两组在同一条件下各跑多次再比较。

**3.（中低）首次 `recover()` 失败后，重试会跳过完整性检查**

- 位置：`HistoryStore.swift:1116-1128`。`needsRecoveryValidation` 只在恢复成功的末尾置真。
- 触发：首次恢复在版本检查或 Staging 清理处抛错，之后同一实例再次调用 `recover()`。
- 影响：重试时不做 `quick_check` 和外键检查。当前应用只在启动时调用一次，失败后不重试，所以现在不可达；以后加入重试就会带着这个缺口。
- 复现：临时库打开后把 `user_version` 改成 99，调用 `recover()` 失败；改回 6 并插入一条孤儿 `items` 行，再调用 `recover()` 返回成功，第三次才报 `corruptPayload`。
- 建议：在函数开头、任何可能抛错的语句之前就把标记置真，或者改成只有打开校验后的第一次调用才跳过。

**4.（中低）串行化后的偶发超时用例余量仍然很薄**

- 位置：`CommentFeatureTests.swift:176-198`。
- 证据：三次全量运行中，两个参数合计耗时 18.2 s、16.8 s、13.9 s，单个参数的等待上限是 10 s。单独运行时每个约 50 ms。基线上那次失败是 11.3 s。
- 影响：`.serialized` 只让两个参数互不争用，套件仍和其他一百多个套件并行，根因没有消除，全量运行仍可能偶发失败。
- 建议：让这个套件不与其他套件并行（例如放到单独的串行测试计划或加全局串行 trait），不要放宽上限。

**5.（低）测试钩子进入了 Release 二进制**

- 位置：`AppDelegate.swift:49-68`。`hiddenSurfaceTest`、`configureSurfacesForTesting`、`toggleHistoryForTesting` 和提交探针原来在 `#if DEBUG` 内，现在无条件编译；原注释“发布构建不存在替换开关”已被删除。
- 影响：都是 internal 成员，运行时没有入口能触发，行为不变。但发布构建里多了一个能让所有窗口不显示的开关，`presentHistory` 里也多了按它分支的逻辑。
- 建议：确认这是有意的取舍（为了 Release 基准）。如果不是，可以用自定义编译条件代替。

**6.（低）失效文件的提示在三种情况下不够准确**

- 位置：`HistoryView.swift:1338-1345`、`:1450-1455`、`:1499-1501`。
- 只有部分原件缺失时，卡片不显示任何提示（`unknown == count` 才进入）。
- 详情只列前 4 个文件的副本状态，第 5 个起看不到哪些可恢复。
- 说明文字“历史已保存N 个文件副本”在数字前缺一个空格；原来关于“访达同名冲突会停止、不覆盖”的说明被删掉了。

**7.（低，遗留）占用达到配额时 `canCapture` 仍需约 1.5 s**

- 位置：`HistoryStore.swift` 的 `canCapture`。每 60 秒的维护和每次变更后都会调用。
- 本轮的缓存只省掉了聚合查询，预演事务没有变。文档如实记录了这一点，所以不算本轮缺陷，但原报告 F4 在这个场景下的问题还在。

**8.（低，既有问题被放大）正文损坏时粘贴提示文不对题**

- 位置：`PasteCoordinator.swift:232`。`corruptPayload` 被映射成“所选内容包含无文本项目，不能纯文本输出”。
- 本轮让去重不再读正文，并把 `SQLITE_CORRUPT` 也归为 `corruptPayload`，所以损坏更多地在粘贴时才暴露，用户看到的是这条不相关的提示。
- 复现：临时库入库一条文本，把 `blobs.payload` 清零，对该记录执行原格式复制。

另外两点不是缺陷，但需要更新记录：

- `delivery.md` 开头仍写“全量静默运行未跑完”，与文末补记和本次三次全量通过的结果不一致。
- `delivery.md` 记录的 `sessionCleanupPreservesExternalReferences` 崩溃和 `richTextDocumentThumbnail` 失败，本次在默认环境下没有出现。
